# QR 사진 → 프론트 → 백엔드 → AI 결과 연결 검증

검사일: 2026-11-14 (Asia/Seoul)

## 검증 범위와 결과

**실제 프론트 API 코드와 결과 화면용 데이터 변환을 사용한 통합 E2E 검증: 통과.**

카메라 대신 테스트 사진의 QR을 OpenCV로 읽고, 상표 후보 선택은 테스트 코드에서 명시적으로 수행했습니다.
실제 Expo 카메라·앨범·권한, 휴대폰 화면 렌더링·버튼 터치까지 자동화한 검사는 아닙니다.

| 단계 | 실제 결과 |
| --- | --- |
| 합성 NAVER 안내 사진의 QR 읽기 | 공개 HTTP 리디렉션 테스트 URL 추출 |
| 프론트 → POST /api/ocr/brands | HTTP 200, BAZE AI OCR 성공 |
| 상표 후보 | NAVER / 네이버, 공식 도메인 등록됨 |
| 후보 확인 | 테스트 코드에서 네이버 선택, 확인 전 분석 호출 없음 |
| 프론트 → POST /api/analyze | HTTP 200, brand_texts=[네이버] 전달 |
| 리디렉션 | HTTP 302 → https://example.com → HTTP 200 |
| 최종 주소의 2번 검사 | 네이버 공식 도메인과 불일치 |
| AI 페이지 분석 / 결과 설명 | 둘 다 generated |
| 종합 판정 | 70점 · 위험 |
| 프론트 결과 데이터 | 백엔드와 동일한 70점 · 위험, 최종 주소·불일치 이유 포함 |
| 자동 접속 | auto_open=false, requires_confirmation=true |
| 전체 소요 | 약 9.7초 |

시나리오 URL은 https://httpbin.org/redirect-to?url=https%3A%2F%2Fexample.com 입니다.
실제 공격 사이트를 사용하지 않고, NAVER 안내와 다른 도메인으로 연결되는 상황을 만들었습니다.
70점은 악성 확률이 아닙니다. 상표 불일치 50점 + 리디렉션 매개변수 20점의 규칙 점수입니다.
페이지 AI는 이 예시 본문에서 공격 행동 신호를 찾지 않아 AI 행동 점수는 0이었습니다.
전체 정보 수집 상태는 partial이므로 모든 보안 정보를 확인했다는 뜻은 아닙니다.

## 발견하고 수정한 부분

1. 프론트 .env의 API 주소가 이전 Wi-Fi IP를 가리켰습니다. 검사 당시 현재 PC IP로 갱신했습니다.
2. 백엔드는 최종 URL의 위험을 점수에 넣지만 프론트 검사 목록은 원래 URL만 읽었습니다.
   프론트 src/result/verdict.ts에서 원래·최종 주소를 함께 설명하도록 수정했습니다.
   최종 주소에만 있는 APK·상표 불일치·매장 사칭 등 회귀 테스트 6개를 추가했습니다.
3. 프론트 타입 검사·린트·테스트 18개가 통과했습니다.

## 다시 실행

백엔드의 가상환경, 프론트 npm 의존성, BAZE 설정과 네트워크 연결이 준비되어 있어야 합니다.
테스트 사진 생성·QR 읽기는 OpenCV / NumPy / Pillow와 Windows 맑은 고딕 폰트를 사용합니다.
현재 PC에는 이 의존성이 설치되어 있습니다. 앱의 AI OCR 자체에는 OpenCV가 필요하지 않습니다.

프론트 .env의 EXPO_PUBLIC_API_URL을 현재 PC의 Wi-Fi 주소와 8000 포트로 설정하고,
8000 포트를 사용하는 서버를 종료한 뒤 백엔드 폴더에서 실행합니다.

```powershell
.\.venv\Scripts\python.exe -B -m scripts.run_e2e --live
```

실제 OCR·페이지 분석·설명 AI를 호출하므로 API 사용량이 발생할 수 있습니다.
테스트가 임시 백엔드를 시작하고 끝나면 종료합니다.
다른 서버를 임의로 종료하거나 실제 QR 주소를 휴대폰 브라우저로 열지 않습니다.

- 사진: data/ocr_smoke/e2e/naver-redirect-qr.jpg
- 입력: data/ocr_smoke/e2e/fixture.json
- 결과: data/ocr_smoke/e2e/result.json
- 서버 로그: data/ocr_smoke/e2e/backend.log

사진·결과·로그는 Git에서 제외됩니다. API 키와 사진 base64는 결과 보고서에 기록하지 않습니다.
스크립트는 프론트의 기존 API 함수와 buildVerdict를 직접 호출합니다. 응답을 모의 값으로 대체하지 않습니다.

## 실기기에서 남은 확인

같은 Wi-Fi의 휴대폰에서 http://PC_IP:8000/health가 열리는지 먼저 확인합니다.
Expo Go에서 'QR 사진으로 상표명도 찾기'를 켜고 테스트 사진을 선택한 뒤,
네이버 후보 확인 → 분석 결과의 70점·위험/최종 주소/불일치 이유를 확인합니다.
실제 점수는 다시 조회한 정보에 따라 달라질 수 있습니다.
권한 거부·취소·뒤로가기·중복 터치와 자동으로 QR 사이트가 열리지 않는지도 확인해야 합니다.
동일 PC의 LAN 주소로 성공한 결과만으로 휴대폰의 방화벽·Wi-Fi 접근까지 검증했다고 보지는 않습니다.

## 점수 및 AI 판정 별도 점검

실제 BAZE로 합성 HTML 19건을 검사한 결과와 유사 상표·확인 불가 점수의 한계는 [점수 점검 기록](score_audit.md)을 참고합니다. 정상 외부 SSO의 약한 경고 1건과 JavaScript 화면의 확인 불가 1건을 포함해 기록했습니다.

## AI 공식 도메인 검색으로 전환

현재 공식 도메인 판정은 [매 스캔 AI 웹 검색](ai_domain_verification.md)을 사용합니다. 위의 과거 70점 예시는 당시 정적 도메인 비교 기준입니다. 검색 근거에 따라 현재 결과는 달라지며 근거가 없으면 확인 불가로 남깁니다.

## 현재 정책: 페이지 AI 점수 제외

현재 API는 metadata-v2/combined-v2를 반환합니다. 페이지 AI는 참고 정보이며 종합 점수 및 완료 조건에서 제외합니다.
위의 behavior-v1/combined-v1 사례는 이전 정책 기록입니다. [현재 점수 정책](metadata_scoring.md)을 참고하세요.
